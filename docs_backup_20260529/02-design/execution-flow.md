# 任务执行流程

**版本**: v1.0
**日期**: 2026-05-22
**状态**: 设计阶段

---

## 概述

本文档定义从用户输入任务到团队交付总结的完整端到端流程。流程设计遵循"AI 建议 → 人工确认 → 团队执行 → 持续改进"的人机协作模式。

---

## 流程总览

```
用户输入任务
    │
    ▼
Step 2: AI 分析领域 + 任务类型
    │
    ▼
Step 3: AI 建议角色清单 + 协作策略 + 匹配理由（+ 可选验收标准）
    │
    ▼
Step 4: [用户确认/调整] → 角色匹配 soul → 生成团队实例
    │
    ▼
Step 5-8: 团队内部协作执行（子任务编排 → 分配 → 执行 → 产出）
    │
    ▼
Step 9: [用户审阅] ←→ 修改迭代 → 通过确认
    │
    ▼
Step 10: 团队总结 → 经验入库（记忆/技能/轨迹持久化）
```

---

## Step 1 — 用户输入任务

用户用自然语言描述需要完成的项目总任务。

**输入示例：**
> "我想深入研究王莽新政推行的各项政策，包括经济、政治、社会三个维度，分析其失败原因。"

系统接收后进入 Step 2 分析阶段。

---

## Step 2 — AI 任务分析

AI 分析任务的**领域**和**任务类型**，输出结构化结果。此步骤不涉及 agent 角色，仅分析任务本身。

### 任务领域

| 领域 | 示例 |
|------|------|
| 软件开发 | 功能开发、架构设计、Bug 修复 |
| 政策调研 | 历史研究、政策分析、社会调查 |
| 数据分析 | 数据清洗、统计建模、可视化 |
| 文案写作 | 报告撰写、方案策划、翻译 |
| 设计创意 | UI 设计、品牌设计、内容创作 |
| 其他 | 不属于以上分类的通用任务 |

### 任务类型（四种）

| 类型 | 特征 | 典型场景 |
|------|------|----------|
| **探索研究型** | 信息收集 → 多维分析 → 形成结论 | 调研报告、技术预研、竞品分析 |
| **执行交付型** | 明确需求 → 按步骤执行 → 产出可交付物 | 功能开发、文档撰写、数据处理 |
| **决策分析型** | 多方案比较 → 评估优劣 → 做出选择 | 技术选型、架构评审、投资分析 |
| **创意产出型** | 发散构思 → 迭代打磨 → 成品交付 | UI 设计、文案创作、策划方案 |

当任务涵盖两种以上类型时，标记为**混合型**并列出包含的类型。

### 输出格式

```json
{
  "domain": "政策调研",
  "task_type": "探索研究型",
  "complexity": "中",
  "breakdown": ["经济维度", "政治维度", "社会维度", "综合分析"],
  "analysis": "该项目为历史政策调研，需要多角度信息收集与分析..."
}
```

---

## Step 3 — AI 团队组建建议

AI 根据 Step 2 的分析结果，以结构化文本 + 可编辑卡片的形式建议团队配置。用户可直接修改建议内容。

### 输出内容

**（1）建议的 Agent 角色清单**

每个角色包含：角色名称、职责描述、所需能力。角色清单本身包含数量（几个角色）和身份（每个角色是什么），不需要额外的"数量"字段。

**（2）建议的协作策略**

| 策略 | 工作机制 | 适用场景 |
|------|---------|---------|
| **sequential** (顺序执行) | 1-2 Agent 按序执行，无分工 | 简单线性任务 |
| **hierarchical** (层级委派) | 协调者拆解委派 → 成员执行 → 协调者汇总 | 复杂多模块项目，可并行拆解 |
| **discussion** (圆桌讨论) | 圆桌讨论 → 达成共识 → 按结论执行 | 需要多视角碰撞的决策场景 |

**（3）角色与策略的匹配理由**

说明为什么建议这些角色和这个策略，让用户理解 AI 的推理过程。

**（4）可选：验收标准**

仅当任务类型为"执行交付型"时，AI 同时给出验收标准建议。探索研究型任务不输出验收标准，留待执行中逐步明确。

### 交互方式

用户以**可编辑卡片**形式审阅，可以：
- 修改角色名称、职责
- 增删角色
- 切换协作策略
- 修改验收标准（如有）

AI 建议是起点，不是固定选项。

---

## Step 4 — 用户确认 & 团队生成（人工干预点）

用户确认 Step 3 的建议后，系统执行两个动作：

### 4.1 角色匹配 Soul

Step 3 建议的"角色身份"（如"政治制度分析师"）与 soul 池中的人格模板匹配：

```
建议角色              匹配的 Soul
─────────────────────────────────────
调研协调员      →     agent_mu（权衡分析型）
政治制度分析师  →     agent_heng（深入钻研型）
经济社会分析师  →     agent_ning（沉稳迭代型）
```

匹配依据：角色所需能力与 soul 人格特征的契合度。

### 4.2 生成团队实例

匹配完成后，系统为每个角色创建 agent 实例：

```python
agent_instance = {
    "soul":       "agent_heng",         # 底层的灵魂模板（复用）
    "role":       "政治制度分析师",     # 本次任务的角色身份
    "project_id": "project_王莽调研",   # 所属项目
    "memory":     {...},                 # 独立记忆空间
}
```

**关键设计：Soul 复用，角色映射，记忆隔离。**

### Soul 与 Agent 的目录结构

Soul 池（`backend/agents/agent_xxx/`）的完整结构：

```
backend/agents/agent_heng/
  ├── soul.md              # 人工编写，定义人格（只读）
  ├── growth.json          # 自动生成，进化摘要（读写）
  └── trajectory/          # 自动生成，最近 N 条任务轨迹快照
        ├── 2026-05-20_王莽调研.json
        └── 2026-05-18_宋代官制.json
```

| 层级 | 存储 | 说明 |
|------|------|------|
| **soul.md** | 文件 | 人工维护，定义"我是谁"。只有人能改 |
| **growth.json** | 文件 | 自动生成，进化的"简历"——掌握技能、成功率 |
| **trajectory/** | 文件 | 最近任务轨迹快照，可读、可移植 |
| **记忆/技能/轨迹（全量）** | 数据库 | 运行时检索，语义搜索，全量持久化 |

**自我进化的实现方式：**

```
任务执行 → TrajectoryRecorder 记录每一步决策和结果
    │
    ▼
任务完成 → ExperienceExtractor 提取经验
    │
    ▼
SkillManager 生成可复用技能 → 存入 skills 表 + 更新 growth.json
    │
    ▼
同一 soul 的下次任务 → SkillMatcher 匹配相关技能 → 自动应用
```

- **进化的是**技能库（skills 表）、经验轨迹（trajectories 表）、长期记忆（L3 级 memory_entries）
- **进化的不是** soul.md（人格不变）
- soul.md 修改走人工审核路径：系统发现行为模式问题 → 生成建议 → 人工确认 → 更新

---

## Step 5-8 — 团队协作执行（预留）

> **本节内容待后续补充。** 协作执行涉及子任务编排、分配、执行、产出等环节，是流程中最复杂的部分，不同任务类型和协作策略下的执行方式差异较大，需单独设计。

协作执行阶段的核心活动：

- 子任务编排：协调者（或集体讨论）将总任务拆解为子任务
- 任务分配：按角色能力和依赖关系分配子任务
- 独立执行：各 agent 在自己的记忆空间内执行任务
- 协调沟通：按协作策略规则进行 agent 间通信
- 产出汇总：子任务结果汇总为最终交付物

具体设计待后续确认后补充至此文档。

---

## Step 9 — 用户审阅 & 验收循环（人工干预点）

团队产出提交后，进入持续改进-验收循环：

```
产出提交 → 用户审阅
    │
    ├── 通过 → 进入 Step 10（团队总结）
    │
    └── 不通过 → 用户给出修改意见 → 团队继续执行 → 再次提交
                                       ↑
                                      循环直到通过
```

对于探索研究型任务，验收标准在执行过程中逐步明确，Step 9 不做刚性检查，由用户灵活判断。对于执行交付型任务，对照 Step 3 中给出的验收标准检查。

---

## Step 10 — 团队总结 & 经验入库

所有任务确认完成后：

### 10.1 团队总结

由协调者（或全体 agent）生成项目总结：

- 核心结论与发现
- 各 agent 的贡献摘要
- 协作过程的经验教训
- 可沉淀为后续参考的知识点

### 10.2 经验持久化

总结完成后，学习模块介入：

| 产出物 | 存储位置 | 说明 |
|--------|----------|------|
| 任务轨迹 | `trajectories` 表 + `trajectory/*.json` | 完整执行记录 |
| 提取经验 | `memory_entries` 表（L3 级） | 关键决策和知识点 |
| 新技能 | `skills` 表 + `growth.json` | 可复用的能力 |
| 更新能力摘要 | `growth.json` | 技能列表、成功率 |

同一 soul 参与的下一个项目能自动复用积累的经验和技能。

## 人工干预点汇总

| 节点 | 位置 | 干预内容 |
|------|------|----------|
| **确认点 1** | Step 4 | 确认/调整团队角色、协作策略、验收标准 |
| **确认点 2** | Step 9 | 审阅产出、提出修改意见、确认完成 |
